# How the Lacuna Generators Fundamentally Work

*Written 2026-06-02 on `fresh/v1.0-restart` (= tag `v1.0-canonical` = commit `2935cc8`).
Scope: the v1.0 / Lacuna-Survey generator family. Source files cited inline.*

This document explains the **fundamental operation** of the missingness generators — not a
per-generator catalogue, but the one mechanism every generator is a variation of: **what goes in,
what comes out, and how the decision of which cells to set missing is made.** If you understand
this single contract you understand all 64 survey generators (and all ~110 in the general
registry), because they differ only in the *scalar function* that maps a column's values to a
per-cell missing probability.

---

## 0. The one-sentence version

> A generator is a frozen, deterministic-given-RNG function that, given a real complete data
> matrix `X`, returns a boolean **observed-mask** `R` of the same shape, by computing a
> per-cell missing probability `p` from `X` and flipping a coin against it. **The only thing
> that distinguishes MCAR, MAR, and MNAR is *which columns of `X` the probability `p` is allowed
> to look at.***

- **MCAR**: `p` looks at *nothing* in `X` (a constant rate, or a column-/block-structured rate
  that is still independent of any data value).
- **MAR**: `p` for a *target* column looks at a *different, observed* column (the predictor).
- **MNAR**: `p` for a column looks at *that column's own value* — the value that is about to be
  hidden.

Everything else — logistic vs probit vs threshold vs spline links, single vs multi predictor,
skip-logic vs quantile-censoring — is decoration on this three-way distinction.

---

## 1. What goes in / what comes out — the `apply_to` contract

The operative entry point is **`Generator.apply_to(X, rng) -> R`**, used by the semi-synthetic
data path. (There is a second, legacy method `sample(rng, n, d) -> (X_synth, R)` that *also*
fabricates a synthetic `X`; it is **not** used for training — see §6.)

```
apply_to(X: FloatTensor[n, d], rng: RNGState) -> R: BoolTensor[n, d]
        # n = rows (respondents), d = columns (items/variables)
        # R[i, j] == True  -> cell (i, j) is OBSERVED
        # R[i, j] == False -> cell (i, j) is MISSING
```

**Input contract** (`X`): a *complete* (no-missing) real data matrix, already passed through the
**z-scored predictor view** (§3). Every generator assumes columns are roughly standard-normal in
scale. **Output contract** (`R`): a same-shape boolean mask, with the invariant — enforced by the
caller, not the generator — that *no column is 100% missing* (§4).

Concretely, every generator's internal `_compute_missingness` does exactly three things:

1. **Choose the decision variable.** Pick which column(s) of `X` the probability may depend on.
   *This choice is the mechanism class.*
2. **Map values → probability.** Apply a scalar link `f` to those values:
   `p_missing = f(X[:, decision_col])`, where `f` is a sigmoid, a probit CDF, a hard threshold, a
   step/spline, etc. `p_missing` is a length-`n` (or `[n, d]`) tensor in `[0, 1]`.
3. **Flip coins.** Draw `u ~ Uniform[0,1]` of matching shape and set
   `R[:, target] = ~(u < p_missing)`. The Bernoulli draw is the *only* stochastic step and the
   *only* place `rng` is consumed.

That is the whole machine. The rest of this document is "how step 1 differs across the three
classes" plus the plumbing that feeds it.

`base.py` defines the abstract `Generator` with immutable identity (`generator_id`, `name`,
`class_id ∈ {MCAR=0, MAR=1, MNAR=2}`, frozen `params`). `params.py` is an immutable kwargs bag.
A generator is a *frozen specification*: all of its behaviour is fixed at construction; the only
runtime input is `(X, rng)`.

## 2. The decision rule, per class

Let `t` be a target column (the one being made missing) and `p` be the predictor/decision column.

### MCAR — decision depends on *nothing in `X`*
`lacuna/generators/families/mcar/`

The probability is a constant or a *structural* pattern that never reads a data value:

```python
# MCARBernoulli._compute_missingness  (bernoulli.py)
miss_rate = self.params["miss_rate"]
R = rng.rand(n, d) >= miss_rate         # every cell, same rate, independent of X
```

Variants change *where the constant lives*, never *what it reads*:
- **Bernoulli** — one global rate over all cells (`MCAR-Bernoulli-10/30/50`).
- **ColumnMixture / ColumnOrdered / ColumnClustered** — different *fixed* rate per column, drawn
  from a mixture/ramp/cluster scheme. Still no dependence on values.
- **RandomBlocks / Subgroup** — rectangular blocks or a random row-subgroup get an elevated rate.
- **RotatedBooklet** — planned-missing "booklet" design: some columns universally asked, others
  assigned to rotating blocks so a respondent sees only a subset. This is *by design* MCAR (the
  assignment is randomized by the instrument), and it was added specifically to reproduce the
  column-bimodal footprint of PISA/NAEP-style matrix sampling.

Key point: **MCAR missingness is a property of the cell's *position*, never its *content*.**

### MAR — decision depends on a *different, observed* column
`lacuna/generators/families/mar/`

The canonical form (`MARLogistic`, `simple.py`):

```python
target    = params.get("target_col_idx", -1) % d     # column made missing
predictor = params.get("predictor_col_idx", 0) % d    # a DIFFERENT column
if predictor == target: predictor = (target + 1) % d  # enforce p != t

logits    = alpha0 + alpha1 * X[:, predictor]          # reads the PREDICTOR
p_missing = sigmoid(logits)
R[:, target] = ~(rng.rand(n) < p_missing)              # hides the TARGET
```

The defining feature: **the column whose value drives the probability (`predictor`) is *not* the
column being hidden (`target`), and the predictor is itself fully observed.** So the missingness
is "explained" by data the analyst can see.

MAR variants only swap the **link function** or the **number of predictors**:
- **Link shape**: `Logistic` (sigmoid), `Probit` (normal CDF), `Threshold` (two-level hard
  cut), `Polynomial` (sigmoid of a quadratic), `Spline`/`StepFunction` (piecewise), `Kernel`
  (distance-to-reference). Same predictor, different curve.
- **Predictor count**: `MultiPredictor`, `TwoPredictor`, `ThreePredictor`, `WeightedPredictor`,
  `Interactive` (includes a product term). Logit becomes `alpha0 + Σ alpha_k X[:, p_k]`.
- **Strength presets**: `Weak`/`Moderate`/`Strong` fix `alpha1` to a small/medium/large slope.
- **Survey-shaped MAR** (`survey.py`) — these dress the *same* "predictor gates other columns"
  idea in questionnaire language:
  - `SkipLogic` — if a gate column exceeds a threshold, *subsequent* columns are skipped with
    `conditional_rate`. (One answer ⇒ later items not asked.)
  - `Branching` — a branch column bins rows into branches; each branch "asks" a listed set of
    columns and the others are absent for those rows.
  - `SectionLevel` — a gateway value below a threshold drops an entire contiguous *section* of
    columns; later sections drop more easily.
  - `RequiredOptional`, `QuotaBased`, `DemographicGated`, `PartialResponse`, `RealisticSingle` —
    elevated rates over column subsets gated by an observed predictor or quantile.

In every MAR variant the predictor is an *observed* column, so the mechanism is — by Rubin's
definition — ignorable given the observed data.

### MNAR — decision depends on the *column's own (about-to-be-hidden) value*
`lacuna/generators/families/mnar/`

The signature, shared by **every** MNAR generator, is self-reference:

```python
# self_censoring.py — the prototype
for col in affected_cols:               # a random affected_frac of columns
    logits    = beta0 + beta1 * X[:, col]   # reads the SAME column it will hide
    p_missing = sigmoid(logits)
    R[:, col] = ~(rng.rand(n) < p_missing)
```

The probability that a value is hidden depends on **that very value**. High earners decline to
report income; extreme attitudes go unanswered; a measurement below the instrument floor is
recorded as blank. There is no observed column that explains it, which is exactly what makes MNAR
non-ignorable.

Two structural parameters recur across the MNAR family:
- **`affected_frac`** — what fraction of columns get the mechanism (the rest stay fully observed).
  Selected via `rng.choice(d, n_affected, replace=False)`.
- **The self-referential threshold** — most MNAR variants compute a **quantile of the column's own
  values** and censor on one or both tails:
  ```python
  vals      = X[:, col]
  threshold = torch.quantile(vals, percentile/100.0)   # quantile of THIS column
  p_missing = where(vals > threshold, miss_prob, low)   # hide the tail
  ```

MNAR variants differ only in *which part of a column's own distribution* is hidden, or *how
smoothly*:
- **Self-censoring logistic** (`SelfCensorHigh/Low/Weak/Strong`) — smooth sigmoid in the value;
  sign and slope set which tail and how sharply. The *hardest* MNAR to detect (looks gentle).
- **Self-censoring quadratic** (`SelfCensorExtreme`) — censors *both* tails (deviation²).
- **Threshold / Quantile** (`ThresholdLeft/Right/TwoSided`, `SoftThreshold`, `Quantile70/80/90`) —
  sharp censoring above/below/outside a quantile of the column. The *easiest* to detect (leaves a
  truncated observed distribution).
- **Social-desirability / strategic** (`OverReport`, `NonLinearSocial`, `Gaming`, `Volunteer`) —
  censor a *value region* (a tail or a neighbourhood of a value) reflecting respondent incentives.
- **Group-dependent** (`DemographicDependent`, `ColumnSpecificCensor`, `ValueDependentStrength`) —
  the *strength* of own-value censoring varies by group or column, but the dependence is still on
  the column's own value.

(The general registry also has detection-limit `censoring.py`, latent-variable `latent.py`, and
longitudinal `selection.py`/`informative.py` MNAR; the **survey** registry deliberately excludes
these as not single-wave-questionnaire-plausible — see §5.)

**The one test to classify any generator:** look at what `_compute_missingness` reads to build
`p_missing`. Reads nothing in `X` → MCAR. Reads a *different* column → MAR. Reads the *same*
column it hides → MNAR.

## 3. The predictor view — why `X` is z-scored before any decision

`lacuna/data/semisynthetic.py :: _zscore_columns` + `apply_missingness`

The generators were parameterised for **standard-normal `X`** (intercepts like `alpha0 = -0.5`,
slopes like `alpha1 = 3.0`, thresholds at `0.0`). Real catalog columns are not on that scale —
wine alcohol lives on 11–15, income in the tens of thousands. If you feed raw values into
`sigmoid(alpha0 + alpha1 * X[:, p])`, the logit saturates and you get a degenerate "one column
100% missing" pattern. A 2026-04-25 audit found **41 of 116 generators saturated on `wine`**.

The fix is a **predictor view**: before calling `apply_to`, `apply_missingness` z-scores every
column:

```python
X_complete       = torch.from_numpy(raw.data.astype('float32'))   # original scale
X_predictor_view = _zscore_columns(X_complete)                    # standardized
R = generator.apply_to(X_predictor_view, rng)                     # decision on z-scores
X_observed = X_complete * R.float()                               # but OUTPUT keeps real scale
```

Two things matter here and are easy to miss:

1. **The z-scoring affects only *which cells are chosen*, not *what the model sees*.** The decision
   runs on standardized values so the link functions behave as designed; the observed data handed
   downstream is `X_complete * R` — original units, missing = 0. The standardization is a property
   of the *mechanism's domain*, not of the data.
2. **Zero-variance (constant) columns are zeroed out**, not divided by their zero std — so a
   constant predictor contributes nothing rather than producing NaNs/inf. (Fail-safe per Coding
   Bible Rule 1: a degenerate predictor must not silently blow up the mask.)

This is the single most important non-obvious detail of the pipeline: **"semi-synthetic" means the
*missingness decision* is computed on a normalized view of real `X`, while the *observed values*
remain real.** It is what lets one fixed set of generator parameters apply sensibly across 43
heterogeneous real datasets.

## 4. The non-degeneracy guard

After `apply_to`, `apply_missingness` enforces the output invariant that **every column retains at
least one observed cell**:

```python
for col in range(d):
    if R[:, col].sum() == 0:
        rand_row = rng.randint(0, n, (1,)).item()
        R[rand_row, col] = True
```

A 100%-missing column carries no information and would poison both the reconstruction target and
the column-statistic features. Several generators *also* carry their own `if R.sum() == 0:` floor
internally; the loader's per-column guard is the authoritative one. This is a contract the
*downstream* tokenizer relies on, so it is enforced at the boundary that produces `R`.

## 5. The registry and how a run is assembled

A **run** is assembled from three frozen objects plus a loader:

1. **`GeneratorRegistry`** (`registry.py`) — a validated, ordered tuple of generator instances with
   sequential ids `0..K-1`, each carrying its `class_id`. Built from a YAML allow-list by
   `registry_builder.py`, which **auto-discovers** generator classes by scanning `mcar/ mar/ mnar/`
   and matching the `{FAMILY}{Variant}` naming convention, then instantiates the variants the YAML
   names with the YAML's params. The survey run uses **`configs/generators/lacuna_survey.yaml`** →
   **K = 64 generators: 12 MCAR / 33 MAR / 19 MNAR.**

   `lacuna_survey` is a *curated subset* of the 110-generator general registry, restricted to
   mechanisms plausible for a survey collection process and **deliberately excluding**: detection-/
   quantitation-limit censoring (instrument processes), latent-variable & longitudinal MNAR
   (multi-wave, not single questionnaire), competing-events/symptom-triggered (clinical), heavy-
   tailed distributional MCAR (instrument artifacts), and cross-classified admin/EHR block
   patterns. It also drops a handful of MNAR variants whose realised pattern on `bfi` was
   *indistinguishable* from a MAR variant (e.g. low-rate single-column MNAR-Logistic ≡
   MAR-Logistic) — including two patterns that produce identical masks forces the model to assign
   different labels to identical evidence, which is unlearnable noise.

2. **`GeneratorPrior`** (`priors.py`) — a probability distribution over the `K` generator ids.
   The v1.0 run uses the **uniform** prior (each generator equally likely). Because the survey
   registry has 12/33/19 generators per class, uniform-over-generators implies a **class prior of
   ≈ 19% MCAR / 52% MAR / 30% MNAR** — MAR is over-represented at the *exposure* level. (A
   `class_balanced` prior exists to equalize class mass; it is *not* the v1.0 default.)

3. **The `SemiSyntheticDataLoader`** (`semisynthetic.py`) — the only data path. Per batch item it:
   - picks a random real dataset from the pool (survey: 10 train / 2 val datasets),
   - **subsamples rows first** to `max_rows=128` (then applies the generator — equivalent in
     distribution because all generators are row-independent, but ~230× cheaper on wide data),
   - **samples a generator id from the prior**, retrying up to 20× if the generator is incompatible
     with that dataset's `d` (e.g. a MAR generator needs `d ≥ 2`),
   - calls `apply_missingness(raw_sub, generator, rng)` → `(X_observed, R)`,
   - tokenizes the batch and attaches the generator's `class_id` as the **label**.

   The label the model learns is **`registry.class_mapping[generator_id] ∈ {MCAR, MAR, MNAR}`** —
   the *mechanism class of whichever generator punched the holes*. Ground truth exists only because
   *we* chose the generator; on real data it is unrecoverable (see the realism critique).

Determinism: all randomness flows through an explicit `RNGState` that is `spawn()`-ed per batch
item and per generator call. A fixed `seed` (42) + fixed config reproduces the exact same stream of
(dataset, generator, mask) triples — Coding Bible Rule 6.

## 6. `apply_to` vs `sample` — the 2026-01-10 fix worth understanding

Every generator has **two** mask-producing methods, and conflating them was a real bug:

- **`sample(rng, n, d) -> (X_synth, R)`** fabricates a *synthetic* `X` (Gaussian/correlated) **and**
  computes `R` from *that synthetic* `X`. Pure-synthetic path. **Not used in training.**
- **`apply_to(X, rng) -> R`** computes `R` from the *provided real* `X`. Semi-synthetic path. **The
  training path.**

The original semi-synthetic loader called `sample()`, threw away the synthetic `X`, and pasted `R`
onto the real `X`. For MCAR that is harmless (the mask ignores `X` anyway). **For MAR/MNAR it
destroyed the mechanism**: the mask encoded a predictor/self relationship to a *synthetic* column
the model never saw, so relative to the real data the missingness was effectively random — a MAR
mask with no MAR signal. The fix (`apply_to`, computing `R` from the real `X` the model is handed)
is *the* reason MAR and MNAR are learnable at all in this pipeline. If a generator lacks `apply_to`,
`apply_missingness` falls back to `sample()` **with a loud `UserWarning`** — the failure is visible,
not silent.

## 7. End-to-end, in one diagram

```
configs/training/survey.yaml          configs/generators/lacuna_survey.yaml
      │  (dataset pool, max_rows/cols)        │  (allow-list of 64 variants + params)
      ▼                                       ▼
 real survey CSVs ──► DatasetCatalog     registry_builder ──► GeneratorRegistry(K=64)
      │  raw.data [N, d]  (complete)               │                 │
      │                                            ▼                 ▼
      │                                     GeneratorPrior(uniform over 64)
      ▼                                            │
 SemiSyntheticDataLoader (per batch item):         │
   1. subsample rows ─► raw_sub [128, d]           │
   2. gen_id ◄── prior.sample(rng) ────────────────┘
   3. generator = registry[gen_id]
   4. apply_missingness(raw_sub, generator, rng):
        X_complete       = raw_sub.data                      # real scale
        X_predictor_view = zscore(X_complete)                # decision domain
        R = generator.apply_to(X_predictor_view, rng):       # ◄── the decision rule
              p = link( X_view[:, decision_col] )            #     MCAR: none
              R[:, target] = ~(rand < p)                     #     MAR : other col
        guarantee ≥1 observed per column                     #     MNAR: same col
        X_observed = X_complete * R                          # real scale, missing=0
   5. label = class_mapping[gen_id]  ∈ {MCAR, MAR, MNAR}
   6. tokenize ─► batch ─► LacunaModel (MoE)
```

The model's entire supervised signal is: *"here is real data with holes punched by a known
mechanism class — name the class."* The generators are the **operational definition** of that
class. Whether that definition matches how real missingness arises is the subject of the companion
critique, `docs/v1.0-realism-critique.md`.
